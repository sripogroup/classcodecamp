# ปิดแอร์อัตโนมัติเมื่อไฟหลวงใกล้ชนเพดาน — ทำได้ไหม และทำยังไงให้ปลอดภัย

**คำตอบสั้น ๆ: ทำได้ และโค้ดพร้อมแล้ว แต่ต้องเข้าใจข้อจำกัดข้อหนึ่งก่อน ไม่งั้นจะเข้าใจผิดว่าปลอดภัยแล้วทั้งที่ยังไม่ปลอดภัย**

---

## 1. เส้นตายที่กำลังป้องกัน

> ผู้ใช้ไฟฟ้าประเภทที่ 2 หากในรอบเดือนใดมีความต้องการพลังไฟฟ้าเฉลี่ยใน 15 นาทีที่สูงสุด **ตั้งแต่ 30 กิโลวัตต์ขึ้นไป** จะจัดเข้าอยู่ในประเภทที่ 3 และจะกลับมาประเภทที่ 2 ได้เมื่อต่ำกว่า 30 กิโลวัตต์ **ติดต่อกันเป็นเวลา 12 เดือน**

สามอย่างที่ต้องจำ:

| ความเข้าใจผิด | ความจริง |
|---|---|
| "อย่าให้เกิน 30 kW" | ต้องอ่านว่า "อย่าให้**ค่าเฉลี่ย 15 นาที**ของหน้าต่างไหนแตะ 30" |
| "เกินแวบเดียวไม่เป็นไร" | ถูก — มอเตอร์สตาร์ท 60 kW 30 วินาที เฉลี่ยแล้วขึ้นแค่ ~2 kW |
| "เกินหลายเดือนถึงจะโดน" | ผิด — **เดือนไหนเกินแค่ครั้งเดียวก็โดนแล้ว** และติดยาว 12 เดือน |

ดังนั้นตัวเลขที่ต้องเฝ้าคือ **"พีคเฉลี่ย 15 นาทีสูงสุดของเดือนนี้"** ระบบแสดงไว้เป็นตัวเลขใหญ่สุดบนหน้าจอแล้ว พร้อมบอกว่าเหลือระยะอีกกี่ kW

## 2. ⚠️ ข้อจำกัดที่ต้องรู้ก่อนจะไว้ใจระบบนี้

**ระบบนี้ดึงข้อมูลจากคลาวด์ของ Huawei ซึ่งช้าประมาณ 5–10 นาที และดึงได้ทุก 5 นาที (เร็วกว่านี้ FusionSolar จะบล็อก)**

หน้าต่างที่ต้องป้องกันยาว **15 นาที** แปลว่า:

```
เวลาจริง      13:00 ─────────────────── 13:15   หน้าต่างปิด
โหลดพุ่งขึ้น        ↑ 13:02
ระบบเห็นข้อมูล                ↑ 13:10 (ช้าไป 8 นาที)
ระบบสั่งปิดแอร์                  ↑ 13:11
แอร์หยุดกินไฟจริง                  ↑ 13:12   ← เหลือแค่ 3 นาทีจาก 15
```

**สรุปตรง ๆ: ระบบบนคลาวด์ตัวนี้ช่วยได้มาก แต่รับประกันไม่ได้ 100% ว่าจะกันทุกหน้าต่างได้ทัน**

มันเก่งเรื่อง:
- ✅ โหลดที่ค้างนาน ๆ อย่างแอร์ — ซึ่งเป็นสาเหตุหลักของพีคจริง ๆ
- ✅ ดึงระดับพื้นฐาน (baseline) ของทั้งวันให้ต่ำลง พีคเลยไม่มีโอกาสเกิด
- ✅ เตือนล่วงหน้าเป็นวัน/สัปดาห์ว่ากำลังไต่เข้าใกล้เพดาน
- ✅ เก็บสถิติว่าพีคของเดือนอยู่ที่เท่าไหร่ เกิดตอนไหน เพราะอะไร

มันไม่เก่งเรื่อง:
- ❌ โหลดที่พุ่งขึ้นเร็วและอยู่นาน 15 นาทีพอดี (เช่นเดินเครื่องจักรใหญ่พร้อมกัน)
- ❌ รับประกันแบบมีผลผูกพันว่าจะไม่มีหน้าต่างไหนหลุด

## 3. สถาปัตยกรรมที่ควรเป็น: สองชั้น

เมื่อเดิมพันคือค่าไฟแพงทั้งปี ควรมี **สองชั้น** ไม่ใช่ชั้นเดียว

```
┌─ ชั้นที่ 1: ตัวคุมในโรงงาน (ของจริงที่ป้องกัน) ────────────┐
│  มิเตอร์ของตัวเอง ──RS485──► ESP32/PLC ──► รีเลย์ ──► แอร์  │
│  • อ่านค่าทุก 1-2 วินาที ไม่ผ่านอินเทอร์เน็ต               │
│  • คำนวณหน้าต่าง 15 นาทีเอง สั่งตัดได้ในไม่กี่วินาที        │
│  • เน็ตหลุด ไฟดับ คลาวด์ล่ม ก็ยังทำงาน                    │
└────────────────────────────────────────────────────────┘
                          ▲ ถามสถานะ/นโยบาย
┌─ ชั้นที่ 2: Solar Guard บนคลาวด์ (ตัวนี้) ─────────────────┐
│  • เตือนคนล่วงหน้า + บอกให้ไปปิดอะไร                      │
│  • ติดตามพีคของเดือน + เตือนเมื่อเข้าใกล้เพดาน            │
│  • สั่งตัดโหลดช้า ๆ (แอร์) + รายงาน + เก็บประวัติ          │
│  • หน้าจอติดผนัง + Telegram + อีเมล                       │
└────────────────────────────────────────────────────────┘
```

**ถ้าจะเลือกทำอย่างเดียวเพราะงบจำกัด** — เริ่มจากชั้นที่ 2 (ตัวนี้ ฟรี) ใช้ 1–2 เดือนดูก่อนว่าพีคจริงอยู่ที่เท่าไหร่และเกิดจากอะไร ถ้าพบว่าพีคเฉียด 30 บ่อย ค่อยลงทุนชั้นที่ 1 (~5,000 บาท) ซึ่งถูกกว่าค่าไฟส่วนต่างเดือนเดียว

### ของที่ต้องซื้อสำหรับชั้นที่ 1

| ของ | ราคาโดยประมาณ | หมายเหตุ |
|---|---|---|
| มิเตอร์ Modbus RS485 + CT (เช่น SDM630 / PZEM-016) | 1,500–3,000 บาท | **ติดแยกต่างหาก** อย่าไปแย่งบัส RS485 ของ Huawei ที่ต่อ SmartLogger อยู่ |
| ESP32 + โมดูล RS485 (MAX485) | 250–400 บาท | |
| โมดูลรีเลย์ + คอนแทกเตอร์ตามจำนวนโซน | 300–800 บาท/โซน | ส่วน 220V ให้ช่างไฟต่อ |
| กล่อง + อะแดปเตอร์ + สายไฟ | 500 บาท | |

> ⚠️ อย่าต่อ ESP32 เข้าบัส RS485 เส้นเดียวกับที่ SmartLogger ของ Huawei ใช้อยู่ — จะมี master สองตัวชนกันแล้วข้อมูลรวนทั้งระบบ ให้ติดมิเตอร์ตัวใหม่แยกไปเลย

## 4. ทำไม Cloudflare สั่งรีเลย์ตรง ๆ ไม่ได้ (และแก้ยังไง)

Cloudflare Workers อยู่บนอินเทอร์เน็ต **เรียกเข้า `192.168.x.x` ในโรงงานไม่ได้** ถ้าจะให้เรียกได้ต้องเปิดพอร์ตออกเน็ต ซึ่ง**ไม่ควรทำเด็ดขาด** (เท่ากับเปิดให้ใครก็ได้สั่งรีเลย์ในโรงงาน)

ระบบนี้เลยใช้ **โหมด pull** แทน — ฝั่งโรงงานเป็นคนถามเข้ามาเอง:

```
ESP32 ในโรงงาน ──(ทุก 20 วินาที)──► GET /api/zones ──► Cloudflare
                ◄── {"ac_office2":{"power":"off"}, ...}
                └─► สั่งรีเลย์ตามนั้น
```

ข้อดี: ไม่ต้องเปิดพอร์ตอะไรเลย ไม่ต้องมี IP จริง ปลอดภัยกว่ามาก

**Fail-safe ที่สำคัญ**: ถ้าข้อมูลใน Cloudflare เก่าเกิน 20 นาที `/api/zones` จะตอบว่า `stale: true` และสั่งให้**เปิดทุกโซนกลับ** — เพราะ "ระบบเงียบ" ต้องไม่แปลว่า "ปิดแอร์ค้างไว้ตลอดกาล" และ ESP32 เองก็ต้องเปิดทุกโซนกลับถ้าต่อเน็ตไม่ได้เกิน 5 นาที

## 5. ตั้งค่าโซน

ตั้งที่ตัวแปร `ZONES` ใน `wrangler.toml` เป็น JSON:

```json
[
  {"id":"ac_office2","name":"แอร์ออฟฟิศชั้น 2","kw":12,"priority":1,"driver":"pull"},
  {"id":"ac_meeting","name":"แอร์ห้องประชุม","kw":6,"priority":2,"driver":"pull"},
  {"id":"pump_backup","name":"ปั๊มน้ำสำรอง","kw":7,"priority":3,"driver":"pull"},
  {"id":"ac_server","name":"แอร์ห้องเซิร์ฟเวอร์","kw":4,"priority":9,"driver":"pull","protected":true}
]
```

| ฟิลด์ | ความหมาย |
|---|---|
| `id` | รหัสไม่ซ้ำ ใช้อ้างอิงในตัวควบคุม |
| `name` | ชื่อที่จะขึ้นในข้อความแจ้งเตือน |
| `kw` | **ต้องวัดจริงด้วยแคลมป์มิเตอร์** ระบบใช้เลขนี้คำนวณว่าต้องปิดกี่ตัว |
| `priority` | น้อย = ยอมให้ปิดก่อน (กระทบคนน้อยสุด) |
| `protected` | `true` = ห้ามแตะเด็ดขาด (ห้องเซิร์ฟเวอร์ ห้องคุมเครื่อง ห้องยา) |
| `driver` | `pull` (แนะนำ) / `shelly` / `sensibo` / `webhook` |

## 6. กฎความปลอดภัยที่ระบบบังคับให้เสมอ

คอมเพรสเซอร์แอร์พังง่ายกว่าที่คิด ถ้าโดนเปิด-ปิดถี่ ๆ ระบบจึงบังคับกฎพวกนี้ตายตัว:

| กฎ | ค่าเริ่มต้น | เหตุผล |
|---|---|---|
| `AUTOSHED_MIN_OFF_MIN` | 10 นาที | ปิดแล้วต้องปิดค้างขั้นต่ำ ห้ามเปิดกลับทันที (short cycling ทำคอมเพรสเซอร์พัง) |
| `AUTOSHED_MIN_ON_MIN` | 15 นาที | เปิดกลับแล้วต้องได้ทำงานสักพักก่อนโดนสั่งปิดอีก |
| `AUTOSHED_MAX_OFF_MIN` | 30 นาที | ปิดต่อเนื่องนานสุด แล้ว**หมุนเวียนไปปิดโซนอื่นแทน** คนจะได้ไม่ร้อนอยู่โซนเดียวทั้งบ่าย |
| `AUTOSHED_MAX_ZONES` | 3 | ปิดพร้อมกันได้มากสุดกี่โซน |
| `AUTOSHED_RESTORE_GAP_MIN` | 3 นาที | เปิดกลับทีละโซน ไม่เปิดพร้อมกัน (ไม่งั้นสตาร์ทพร้อมกันจะสร้างพีคใหม่ทันที — ประชดตัวเอง) |
| `protected` | – | โซนที่ห้ามแตะ ไม่ว่าจะหนักแค่ไหน |
| `/restore` | – | คนสั่งชนะระบบเสมอ พิมพ์แล้วเปิดกลับทั้งหมด + ระบบเงียบ 30 นาที |

ทุกกฎมีเทสต์คุมอยู่ใน `test/demand.test.js` รันเช็คได้ด้วย `node test/demand.test.js`

## 7. เปิดใช้เป็นเฟส (อย่าข้าม)

| เฟส | `AUTOSHED_MODE` | ทำอะไร | นานแค่ไหน |
|---|---|---|---|
| 1 | `off` | เก็บข้อมูลอย่างเดียว ดูว่าพีคจริงอยู่ที่เท่าไหร่ เกิดตอนไหน เพราะอะไร | 2 สัปดาห์ |
| 2 | `dryrun` | ระบบคิดครบและส่งข้อความว่า "ถ้าเปิดใช้จริงจะสั่งปิด X" แต่ไม่สั่งจริง — เอาไว้ดูว่ามันตัดสินใจสมเหตุสมผลไหม | 2 สัปดาห์ |
| 3 | `on` แต่ใส่แค่ 1 โซน | เปิดจริงกับแอร์ตัวที่กระทบคนน้อยที่สุดก่อน | 2 สัปดาห์ |
| 4 | `on` ครบทุกโซน | ใช้เต็มระบบ | – |

**ห้ามข้ามไปเฟส 3 เลย** ระบบที่ปิดแอร์ผิดจังหวะครั้งเดียวจะถูกสั่งถอดออกทันที แล้วคุณจะไม่ได้ประโยชน์อะไรเลย

## 8. โค้ดตัวควบคุมในโรงงาน (โหมด pull)

ESP32 + โมดูลรีเลย์ 4 ช่อง ไม่ต้องมีมิเตอร์ก็ใช้ได้ (แค่ทำตามที่คลาวด์สั่ง)

```cpp
#include <WiFi.h>
#include <HTTPClient.h>

const char* SSID = "ชื่อWiFiโรงงาน";
const char* PASS = "รหัสWiFi";
const char* URL  = "https://solar-guard.xxxx.workers.dev/api/zones?k=TOKEN";

// ลำดับต้องตรงกับ id ใน ZONES
const char* ZONE_IDS[] = {"ac_office2", "ac_meeting", "pump_backup", "ac_server"};
const int   RELAY_PIN[] = {26, 27, 14, 12};
const int   N_ZONES = 4;

const unsigned long POLL_MS = 20000;
const unsigned long FAILSAFE_MS = 300000;  // ต่อเน็ตไม่ได้ 5 นาที = เปิดทุกโซนกลับ
unsigned long lastOkAt = 0;

void setRelay(int i, bool on) {
  digitalWrite(RELAY_PIN[i], on ? HIGH : LOW);   // HIGH = จ่ายไฟให้โหลด
}
void allOn() { for (int i = 0; i < N_ZONES; i++) setRelay(i, true); }

void setup() {
  Serial.begin(115200);
  for (int i = 0; i < N_ZONES; i++) { pinMode(RELAY_PIN[i], OUTPUT); setRelay(i, true); }
  WiFi.begin(SSID, PASS);
  while (WiFi.status() != WL_CONNECTED) { delay(500); Serial.print("."); }
  lastOkAt = millis();
  Serial.println("\nพร้อมทำงาน");
}

void loop() {
  bool ok = false;

  if (WiFi.status() == WL_CONNECTED) {
    HTTPClient http;
    http.begin(URL);
    http.setTimeout(8000);
    if (http.GET() == 200) {
      String body = http.getString();
      // ถ้าคลาวด์บอกว่าข้อมูลเก่า ให้เปิดทุกโซน (fail-safe ฝั่งคลาวด์)
      if (body.indexOf("\"stale\":true") >= 0 || body.indexOf("\"stale\": true") >= 0) {
        allOn();
      } else {
        for (int i = 0; i < N_ZONES; i++) {
          int at = body.indexOf(ZONE_IDS[i]);
          if (at < 0) continue;
          int p = body.indexOf("\"power\"", at);
          // ปิดเฉพาะเมื่อเจอคำว่า "off" จริง ๆ นอกนั้นเปิดไว้เสมอ
          bool wantOn = !(p >= 0 && body.indexOf("\"off\"", p) >= 0 && body.indexOf("\"off\"", p) - p < 20);
          setRelay(i, wantOn);
        }
      }
      ok = true;
      lastOkAt = millis();
    }
    http.end();
  }

  // fail-safe ฝั่งอุปกรณ์: ติดต่อไม่ได้นานเกินไป = เปิดทุกอย่างกลับ
  if (!ok && millis() - lastOkAt > FAILSAFE_MS) allOn();

  delay(POLL_MS);
}
```

## 9. ปิดแอร์ยังไงดี: ตัดไฟ vs ขยับอุณหภูมิ

| วิธี | ลดโหลดได้ | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **ขยับ setpoint ขึ้น 2–3°C** (IR เช่น Sensibo, Tuya IR) | 10–20% | คนแทบไม่รู้สึก ไม่ทรมานคอมเพรสเซอร์ ไม่ต้องแตะไฟ 220V | ลดได้ไม่เยอะ ต้องมีตัวส่ง IR ต่อแอร์ 1 ตัว |
| **สั่งปิดผ่าน IR** | 100% ของตัวนั้น | ไม่ต้องแตะไฟ 220V แอร์ปิดตัวเองอย่างถูกวิธี | ถ้าใครกดรีโมทเปิดกลับ ระบบไม่รู้ |
| **ตัดไฟด้วยคอนแทกเตอร์** | 100% | บังคับได้จริง ปิดแล้วปิดเลย | ต้องให้ช่างไฟต่อ / แอร์บางรุ่นไม่ auto-restart ตอนไฟกลับ ต้องเช็คก่อน |

**แนะนำให้เริ่มจากขยับ setpoint** — เพราะได้ผลเร็ว ไม่มีใครบ่น และไม่ต้องยุ่งกับไฟ 220V ถ้าลดได้ไม่พอค่อยเพิ่มการสั่งปิดจริงทีหลัง

driver `sensibo` ในระบบนี้รองรับทั้งสองแบบแล้ว ตั้ง `"mode":"setpoint"` พร้อม `normalTemp` / `shedTemp`:

```json
{"id":"ac_office2","name":"แอร์ออฟฟิศชั้น 2","kw":12,"priority":1,
 "driver":"sensibo","apiKey":"xxx","podId":"xxx",
 "mode":"setpoint","normalTemp":25,"shedTemp":28}
```

## 10. เช็กลิสต์ก่อนเปิดโหมด `on`

- [ ] วัด kW จริงของทุกโซนด้วยแคลมป์มิเตอร์แล้ว กรอกลง `ZONES` ตรงกับความจริง
